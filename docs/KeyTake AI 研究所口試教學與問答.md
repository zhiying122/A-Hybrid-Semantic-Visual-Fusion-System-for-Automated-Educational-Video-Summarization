# KeyTake AI 研究所口試教學與問答

> 本教材對照目前程式實作。口試時應將「已實作」、「目前採用設定」、「探索性結果」及「尚未驗證」清楚分開。請勿把技術名稱說成超出程式能力的功能。

## 1. 三個層次理解系統

### 第一層：白話說法

KeyTake AI 像一位幫忙做課堂回顧的助理。它先聽老師說了什麼，再觀察影片裡是否有板書或手部動作等線索，接著把同一時間附近的聲音和畫面分數合在一起，挑出較值得回看的片段，剪成一支短影片並整理片段索引。它不是真的知道老師心裡認為哪個概念最重要；它是依照可計算的線索做排序，最後還受到摘要長度限制。

### 第二層：資工系學生說法

系統以 FastAPI 接受影片上傳，預設交由 Celery/Redis 背景執行 `run_pipeline()`。FFmpeg 負責轉檔及抽音訊；Whisper 產生有時間戳的逐字稿，語意評分器以 TF-IDF/SBERT 或可選 LLM 產生文字特徵。每個逐字稿片段同時對齊韻律量與三個影片影格，視覺分支再以 MediaPipe/GRU、OCR/SBERT 和 CLIP 建立視覺訊號。Adaptive Fusion 以視覺可靠度調整視覺權重，預設 MLP 關閉。選段器套分數門檻、合併及摘要比例上限，FFmpeg 輸出摘要，timeline mapping 將原片時間對到摘要影片時間。

### 第三層：研究所口試技術說法

本研究把教學影片摘要視為時間對齊的多模態排序問題，而非端到端影片理解。ASR 的 segment timestamps 是模態間 join key；文字、視覺、韻律的分數都先以片段為單位生成。Adaptive Fusion 的視覺係數是 \(\beta R_v\)，使視覺可靠度不足時減少視覺貢獻；MLP 則把 12 維手工特徵輸入監督式網路，但目前仍是小樣本實驗、旗標停用。資料切分依影片 group，避免同片相鄰片段洩漏到 validation；訓練與測試都依人工標註 `eval_range_sec` 裁切。現有四片、單人標註和過往對 `test_10min` 的參數掃描，均限制了泛化結論；因此只報告觀察值，不聲稱已證明優於基線。

## 2. 重要技術教學卡

### 2.1 FastAPI、Celery 與資料流

1. **是什麼？** FastAPI 是 HTTP API 框架；Celery 是背景工作佇列，Redis 在此作 broker/backend。
2. **為何需要？** 影片推論時間長，不適合讓上傳 HTTP 請求一直等待。
3. **負責工作？** 接收影片、回 task ID、排程摘要、回報狀態及提供結果檔。
4. **程式位置？** [`keytake_api_optimized.py`](../keytake-ai/src/platform/keytake_api_optimized.py)、[`celery_app.py`](../keytake-ai/src/platform/celery_app.py)、[`api.py`](../keytake-ai/src/platform/api.py)。
5. **如何執行？** `/upload` 驗證和儲存，再派送 `process_video_task`；前端每兩秒輪詢 `/status/{task_id}`。
6. **輸入／輸出？** multipart 影片 → UUID、狀態、摘要 mp4、索引、時間 mapping。
7. **算法？** 非同步佇列／狀態機，不是 AI 模型。
8. **拿掉會怎樣？** CLI 仍能跑管線，但不能使用目前的 Web 上傳與非同步任務介面。
9. **限制？** 同步 fallback 的狀態存在記憶體；API 沒有登入權限，不可直接視為公開服務。
10. **可能提問？** 為什麼不直接在 HTTP request 跑完整摘要？
11. **回答？** 長影片工作可能超過請求時限，因此先回 task ID、背景處理，再由前端查狀態。Redis/worker 不可用時預設回 503，而非假裝已排入任務。

### 2.2 音訊前處理與 SNR

1. **是什麼？** 音訊抽取、取樣率轉換及條件式降噪。
2. **為何需要？** Whisper 與韻律分析需要一致的音訊格式；噪音可能降低辨識品質。
3. **負責工作？** FFmpeg 輸出 16 kHz、mono、PCM WAV；估算音訊底噪並決定是否頻譜減法。
4. **位置？** [`preprocessor_optimized.py`](../keytake-ai/src/preprocessing/preprocessor_optimized.py)：`extract_audio()`、`estimate_snr()`。
5. **如何執行？** 音訊切成 25 ms frame、10 ms hop，計算各 frame mean-square power。
6. **輸入／輸出？** 原影片 → WAV、啟發式 SNR、是否 denoise 的 metadata。
7. **公式？** \(\widehat{SNR}_{dB}=10\log_{10}(\bar P/P_{10})\)，\(\bar P\) 為平均 frame power，\(P_{10}\) 為最低 10 百分位 frame power。例：平均功率 100、底噪估值 1，估計 \(10\log_{10}(100)=20\) dB。
8. **拿掉會怎樣？** Whisper 仍可讀 WAV，但前處理不會統一或條件式抑噪。
9. **限制？** 沒有乾淨參考訊號，這不是嚴格測量 SNR；目前資料不足以校準 10 dB 門檻。
10. **可能提問？** 你如何知道環境噪音是 1？
11. **回答？** 程式以低能量 frame 分位數近似噪音底，並未有參考噪音軌，所以只能稱為 heuristic estimate，不能說是實測信噪比。

### 2.3 Whisper 語音辨識

1. **是什麼？** 將音訊轉為文字及時間戳片段的 ASR 模型。
2. **為何需要？** 讓文字語意與片段時間對齊，供融合及原片剪輯使用。
3. **負責工作？** 產生 `{start,end,text}`，並以時間戳對應畫面及韻律。
4. **位置？** [`transcriber_optimized.py`](../keytake-ai/src/semantic/transcriber_optimized.py)：`transcribe_with_metadata()`。
5. **如何執行？** `WHISPER_MODE=local` 使用 `WHISPER_MODEL`，預設 `base`；remote 會呼叫 OpenAI transcription endpoint。
6. **輸入／輸出？** WAV → 有起迄秒數的文字片段及 backend metadata。
7. **原理？** Whisper 是以大量弱監督語音資料訓練的序列模型；專案把模型輸出作為片段資料，不自行重訓 ASR。
8. **拿掉會怎樣？** 少了逐字稿，就無法計算文字語意分數、ASR 關鍵字或逐句韻律字元率。
9. **限制？** 轉錄錯字會向下游傳播；目前重複處理不是普遍 hallucination detection。
10. **可能提問？** local 與 remote 的隱私差異？
11. **回答？** 本機模式將音訊交給本機模型；遠端模式會把音訊傳至 API。遠端失敗可按程式路徑嘗試 local fallback；若沒有可用本機模型，會出錯，不能宣稱永遠可降級成功。

### 2.4 TF-IDF 與 SBERT 文字特徵

1. **是什麼？** TF-IDF 衡量詞在本片語料中的相對辨識度；SBERT 將句子映射至語意向量。
2. **為何需要？** 建立每個轉錄片段的文字重要性排序特徵。
3. **負責工作？** 對片段提示語料相似度與詞權重形成 `s_text`，另產生階段及短摘要欄位。
4. **位置？** [`semantic_scorer_optimized.py`](../keytake-ai/src/semantic/semantic_scorer_optimized.py)：`tfidf_scores()`、`sbert_scores()`、`score()`。
5. **如何執行？** TF-IDF 每片段詞權重平均並批次內縮放；SBERT 將片段和提示句編碼、normalize、取 cosine 最大值。
6. **輸入／輸出？** ASR 字串 → `s_text∈[0,1]`、`teaching_stage`、`segment_summary`。
7. **公式？** \(\text{TFIDF}(t,d)=\text{TF}(t,d)\log(N/DF(t))\)。cosine \(=\frac{a\cdot b}{\|a\|\|b\|}\)。預設 SBERT 模式取 `0.5×TFIDF + 0.5×SBERT`。
8. **拿掉會怎樣？** 系統仍可有視覺訊號，但失去語意排序；無 ASR 時更難產生可讀索引。
9. **限制？** 批次內相對分數不是機率；提示語料偏差會影響 SBERT；SBERT/TF-IDF 不會自動產生教學階段分類。
10. **可能提問？** 為什麼使用最大 cosine，而不是平均？
11. **回答？** 程式取與提示語料中最相近的句子，表示「至少有一個提示方向相近」；但這也可能讓單一偶然相似句抬高分數，需以標註驗證。

### 2.5 CLIP

1. **是什麼？** 以圖文對比學習建立共同影像／文字嵌入空間的模型。
2. **為何需要？** 比較片段影格 ROI 與 ASR 關鍵詞是否具語意對齊線索。
3. **負責工作？** 產生額外視覺分數，再與 OCR 視覺分數混合。
4. **位置？** [`clip_scorer.py`](../keytake-ai/src/visual/clip_scorer.py)：`compute_clip_score_with_keywords()`。
5. **如何執行？** 載入 `openai/clip-vit-base-patch32`，processor 處理 ROI/文字，encoder 產生 embedding。
6. **輸入／輸出？** RGB ROI + 關鍵字 → cosine similarity 分數。
7. **公式？** \(c=\frac{v_i\cdot v_t}{\|v_i\|\|v_t\|}\)。例如 cosine 0.7 表示向量方向相近，**不是** 70% 的機率。
8. **拿掉會怎樣？** 視覺打分仍可用 OCR/文字比對路徑，但少一個圖文對齊訊號。
9. **限制？** 文字短語及 ROI 品質會影響相似度；原始 CLIP 分數未寫入 cache，沒有足夠資料支持 CLIP sweep。
10. **可能提問？** 為什麼 CLIP 不直接判斷這張圖很重要？
11. **回答？** CLIP 計算的是預訓練圖文表示的相似程度，不是以本研究人工摘要標註校準的教學重要性機率；必須再與其他特徵及人工評估搭配。

### 2.6 MediaPipe 與手勢軌跡

1. **是什麼？** MediaPipe Hand Landmarker 是手部關鍵點偵測器；GRU 是序列分類器。
2. **為何需要？** 手勢位置／軌跡可作為板書互動的視覺線索之一。
3. **負責工作？** 取第一隻手食指尖、平滑軌跡、分類預設手勢類別、決定是否裁 ROI。
4. **位置？** [`hand_tracker.py`](../keytake-ai/src/visual/hand_tracker.py)、[`gesture_classifier.py`](../keytake-ai/src/visual/gesture_classifier.py)。
5. **如何執行？** MediaPipe landmark 正規化座標乘影格寬高；Kalman filter 平滑；20×4 位置與位移輸入 GRU。
6. **輸入／輸出？** 影片影格 → 手指軌跡、gesture label、intent score、ROI 中心。
7. **算法？** 座標差分形成 dx/dy；GRU 從時間序列輸出五類 logits，softmax 機率經映射成 intent score。
8. **拿掉會怎樣？** 不再以手勢觸發手部 ROI 或按 intent score 調整視覺分數，其他 OCR/CLIP 視覺路徑仍可能運作。
9. **限制？** 找到手不表示理解教學意圖；未偵測到手可能是遮擋或鏡頭裁切，不是「沒有重要內容」。
10. **可能提問？** 你有沒有使用手部 confidence？
11. **回答？** 可靠度模組可接受 confidence 訊號，但目前 `HandTracker.process_frame()` 沒有把 MediaPipe confidence 傳出，因此實際估計會依可用訊號重新加權，不應說每幀都使用 confidence。

### 2.7 韻律特徵

1. **是什麼？** 描述說話速度、振幅、基頻變化及低能量停頓比例的聲學特徵。
2. **為何需要？** 讓融合除文字內容外，也能取得講者表達方式線索。
3. **負責工作？** 逐片段建立 `s_prosodic` 及 `prosodic_available`。
4. **位置？** [`prosodic_analyzer_optimized.py`](../keytake-ai/src/semantic/prosodic_analyzer_optimized.py)。
5. **如何執行？** 按 Whisper 時間範圍裁音訊；計算文字字元/秒、RMS、pyin F0 相對變異與低能量 frame 比例。
6. **輸入／輸出？** WAV+ASR 片段 → 韻律分數和可用遮罩。
7. **算法？** 有效片段的各量以本片 P10/P90 縮放，再按設定權重組合；缺資料以 0.5 佔位但 mask=false。
8. **拿掉會怎樣？** 主 Adaptive Fusion 仍可算；韻律倍率不再調分，MLP feature 缺一模態。
9. **限制？** 語速只是字元率，音量受收音增益影響，音高受 pyin 錯誤影響；不代表重要性真值。
10. **可能提問？** 為什麼對每部影片各自正規化？
11. **回答？** 各指標量綱不同，片內 P10/P90 可形成相對尺度；代價是跨影片分數不再具有共同絕對量尺，且本片 outlier 會影響映射。

### 2.8 Adaptive Fusion

1. **是什麼？** 以視覺可靠度調整視覺模態權重的解析式融合。
2. **為何需要？** 手勢、畫面文字、OCR 等證據的品質會隨影格改變。
3. **負責工作？** 將文字分數、視覺分數、可靠度轉成單一片段分數。
4. **位置？** [`adaptive_fusion.py`](../keytake-ai/src/fusion/adaptive_fusion.py)：`fuse_scores()`；主程式接在 `main.py`。
5. **如何執行？** \(\beta_{\rm eff}=\beta R_v\)，\(\alpha_{\rm eff}=1-\beta_{\rm eff}\)。
6. **輸入／輸出？** \(s_t,s_v,R_v,\alpha,\beta\) → 融合分數。
7. **公式及例子？** \(\alpha=.6,\beta=.4,R=.5,s_t=.8,s_v=.6\)：\(\beta_{\rm eff}=.2\)，所以 \(S=.8×.8+.2×.6=.76\)。
8. **拿掉會怎樣？** 可改固定權重，但低可靠度的視覺線索不再自動降權。
9. **限制？** 可靠度啟發式未充分校準；α/β 搜尋只有三部訓練片，候選 0.5/0.5 未正式採用。
10. **可能提問？** Adaptive 一定比 static 好嗎？
11. **回答？** 不一定；歷史四片數值中 static 高於 adaptive。公式是設計假設，需以未參與選參的多樣測試影片驗證，不宣稱現有結果證明改善。

### 2.9 MLP Fusion 與訓練

1. **是什麼？** 多層全連接前饋神經網路，從特徵及二元標籤學習非線性映射。
2. **為何需要？** 與手工固定權重比較，測試模型能否從人工區段標註學特徵組合。
3. **負責工作？** 將 12 維片段特徵輸出 sigmoid 分數。
4. **位置？** [`mlp_fusion.py`](../keytake-ai/src/fusion/mlp_fusion.py)、[`train_mlp_fusion.py`](../keytake-ai/tools/train_mlp_fusion.py)。
5. **如何執行？** 12→32→16→1；ReLU、Dropout 0.3、sigmoid；BCELoss、Adam；依影片 ID group split。
6. **輸入／輸出？** 5 個分數、韻律可用 mask、6 階段 one-hot → `[0,1]` scalar。
7. **學習目標？** segment 與 GT 重疊比例至少 0.5 設 label=1，否則 0；輸出作為分類分數，並非自動校準機率。
8. **拿掉會怎樣？** 目前主流程本來就預設 Adaptive Fusion；移除 MLP 不改預設路徑。
9. **限制？** 僅四部特徵、三片訓練/驗證、單人標註；MLP 旗標停用，不能宣稱泛化。
10. **可能提問？** 如何避免同影片片段洩漏？
11. **回答？** `groups` 為每個片段的影片 ID，先將唯一 ID 分派至 train 或 validation，片段不自行隨機拆分；獨立測試影片另外提供。過往 test_10min β 掃描仍要揭露，不能稱其全程 untouched。

### 2.10 摘要選段與 FFmpeg

1. **是什麼？** 依分數及時間限制選候選片段、剪輯並串接成摘要。
2. **為何需要？** 融合分數本身不是影片，還要做時序選擇與媒體輸出。
3. **負責工作？** 套門檻、合併、切割過長候選、限制總長度、產生摘要與 timeline。
4. **位置？** `semantic_sliding_window()` 在 `adaptive_fusion.py`；輸出在 [`video_exporter_optimized.py`](../keytake-ai/src/output/video_exporter_optimized.py)。
5. **如何執行？** candidates 依分數排名直到預算用完，最後依原片時間排序，FFmpeg encode/concat。
6. **輸入／輸出？** 原片時間範圍與分數 → summary.mp4、index.json、timeline.json。
7. **公式？** 時間預算 \(B=T×r\)；預設 \(r=0.6\)。若 240 秒影片，預算 144 秒。
8. **拿掉會怎樣？** 仍能評分，但無法決定輸出區段或生成摘要影片。
9. **限制？** 分數高不保證入選，會受門檻與預算競爭；`MIN_SUMMARY_SEC` 不是總摘要保底。
10. **可能提問？** 影片輸出時間怎樣對應原片？
11. **回答？** timeline mapping 記錄每個原片 source interval 與摘要 output interval；前端摘要模式用 output 區間定位，索引維持 source 時間。

## 3. 教授可能提出的 40 題

每題都包含問題、教授要確認的能力、可直接回答、深入追問、追問回答及目前限制的誠實表述。

### 系統架構

#### 1. 請說明系統從上傳到摘要的主要流程。
- **確認：** 是否理解端到端資料流，而非只背模組名稱。
- **直接回答：** 前端上傳到 FastAPI，Celery/Redis 背景呼叫 `run_pipeline()`；音訊轉錄、文字/韻律分析與畫面/手勢/OCR/CLIP 分支在片段時間上對齊，融合後按摘要預算選段，以 FFmpeg 輸出影片及 mapping。
- **追問：** 片段時間如何跨模態對齊？
- **追答：** Whisper `{start,end}` 是 join key，視覺依該片段 25%、50%、75% 時間取樣，音訊韻律也依相同範圍裁切。
- **誠實界線：** 目前不是端到端影片理解模型；各分支仍是啟發式或預訓練模型特徵。

#### 2. 為什麼使用 Celery 與 Redis？
- **確認：** 是否能區分 Web request 與長時間推論。
- **直接回答：** 上傳後立即回 task ID，影片處理由 worker 執行，前端輪詢狀態，避免 HTTP request 被長工作佔住。
- **追問：** Redis 或 worker 停止時怎樣？
- **追答：** 上傳會先探測 Redis，無法派送就回 HTTP 503；只有明確啟用同步 fallback 才用 API 程序內的執行緒。
- **誠實界線：** fallback task store 不持久，API 重啟會失去狀態，不適合 production。

#### 3. 為什麼原片與摘要需要兩套時間？
- **確認：** 是否理解剪輯後時間重置。
- **直接回答：** 摘要片的第 20 秒可能來自原片不同時間；timeline.json 需要把 source interval 對到 output interval，否則點摘要時間軸無法在正確位置播放。
- **追問：** 索引時間是哪一種？
- **追答：** index 保留原片時間；播放摘要時由 timeline mapping 尋找摘要輸出時間。
- **誠實界線：** mapping 由編碼片段 probe 長度估算，不是逐影格精密追蹤。

### 影片處理

#### 4. 為什麼先把影片標準化？
- **確認：** 是否知道媒體輸入的差異。
- **直接回答：** 以 FFmpeg 轉成固定 MP4/H.264、30 fps，並抽 16 kHz 單聲道 WAV，降低下游工具對 codec、frame rate、音訊格式差異的負擔。
- **追問：** 轉碼會不會改變時間？
- **追答：** 可能有 codec time-base 或取樣誤差；原始 duration 與輸出 duration 會以 probe 驗證，剪輯 mapping 也依實際輸出長度校準。
- **誠實界線：** 轉碼不是無損保證，也沒有逐影格補償所有來源影片的異常時間戳。

#### 5. 視覺分支為什麼每個語音片段取三幀？
- **確認：** 是否理解計算量與單幀噪聲的取捨。
- **直接回答：** 以片段 25%、50%、75% 位置取樣，增加代表性又控制 CLIP/OCR/手勢運算量，最後以視覺分最高的一幀作該段代表。
- **追問：** 這樣會不會漏掉短暫板書？
- **追答：** 會有可能；三點取樣不是連續影格分析，密集掃描會增加成本，需未來以成本/召回實驗比較。
- **誠實界線：** 系統沒有保證捕捉片段內所有視覺事件。

### Whisper

#### 6. Whisper 在專案裡輸出什麼？
- **確認：** 是否知道時間對齊格式。
- **直接回答：** 以 `{start,end,text}` 秒為單位輸出逐字稿片段；下游將它對齊畫面、韻律和剪輯。
- **追問：** 為什麼不只保留整段轉錄？
- **追答：** 整段文字沒有時間位置，無法為每個句子配畫面分數或做片段剪輯。
- **誠實界線：** 目前沒有完整詞級 timestamp，主要以 segment-level 對齊。

#### 7. 本機與遠端 Whisper 有何不同？
- **確認：** 是否知道運算與隱私取捨。
- **直接回答：** local 使用設定的 Whisper 模型於本機推論；remote 把音訊送到 OpenAI transcription API，可能有不同延遲、成本與資料處理政策。
- **追問：** 本機缺模型時會不會自動呼叫遠端？
- **追答：** local 路徑不會因模型缺失自動改送遠端；remote 失敗的 fallback 路徑會嘗試 local。
- **誠實界線：** 下載模型權重首次仍可能需要網路。

#### 8. 目前有沒有 Whisper 幻覺過濾？
- **確認：** 是否能對照術語與實作。
- **直接回答：** 沒有一般 hallucination detector；目前檢查有效時間/文字並合併相同文字且高度重疊的重複片段。
- **追問：** 為什麼這兩者不同？
- **追答：** 去重只判斷相同或重疊片段，不能判斷一段看似正常文字是否與音訊內容不符。
- **誠實界線：** README 舊版本「幻覺過濾」用語已校正，口試也應採精確描述。

### TF-IDF／SBERT

#### 9. TF-IDF 的 TF 與 IDF 各代表什麼？
- **確認：** 是否理解詞頻與稀有性。
- **直接回答：** TF 是詞在文件/片段中的頻率，IDF 依詞出現在多少文件來降低常見詞權重。
- **追問：** 為何有助於片段排序？
- **追答：** 相對少見、但在片段中突出的詞可能提供辨識內容線索；本程式取片段非零詞權重平均，再依本批最大值縮放。
- **誠實界線：** 詞罕見不等於教學重要。

#### 10. SBERT 和 TF-IDF 有何差異？
- **確認：** 是否能分辨詞面統計與語意嵌入。
- **直接回答：** TF-IDF 主要依詞項重合與頻率；SBERT 以句向量 cosine 比較語意方向，即使字面詞不同仍可能相近。
- **追問：** 本專案怎樣合併？
- **追答：** SBERT mode 預設 `s_text=0.5*TFIDF+0.5*max-cosine`；各分數不是經人工校準的機率。
- **誠實界線：** 相似度受 prompt corpus、模型領域與短句長度影響。

#### 11. 語意分數是否等於教學重要性的真實機率？
- **確認：** 是否避免過度解讀分數。
- **直接回答：** 不是；它是本系統的相對排序特徵，沒有做 probability calibration。
- **追問：** 要怎樣校準？
- **追答：** 擴大多標註者資料，以獨立影片做 calibration/validation，再用可靠度曲線或 Brier score 等檢查機率校準。
- **誠實界線：** 現有單人標註 pilot 不足以做穩健校準。

### CLIP

#### 12. CLIP 的共同向量空間有什麼用？
- **確認：** 是否理解 image/text encoders 的對齊。
- **直接回答：** Image Encoder 與 Text Encoder 將兩種輸入映到可比較的向量空間，用 cosine 表示方向相似程度。
- **追問：** 這個 cosine 能否當機率？
- **追答：** 不能；相似度沒有以本專案標籤校準為機率。
- **誠實界線：** 本系統使用預訓練 CLIP，不是以本地四片影片重新訓練。

#### 13. CLIP 分數如何形成？
- **確認：** 是否了解實際資料流。
- **直接回答：** 取片段視覺 ROI 和 ASR 文字關鍵字，算 image/text embedding cosine，對關鍵字候選取平均；再依 CLIP_WEIGHT 與 OCR 視覺分混合。
- **追問：** 何時不做混合？
- **追答：** CLIP 不可用或分數沒有大於零時，使用 OCR 路徑視覺分。
- **誠實界線：** `CLIP_SCORE_THRESHOLD` 目前沒有在該路徑實際用來篩分數。

#### 14. 有證據支持 CLIP_WEIGHT=0.3 最佳嗎？
- **確認：** 是否分清現行參數與 sweep 結果。
- **直接回答：** 0.3 是現行程式設定，不是由已記錄 sweep 證實的最佳值；0.5611 的 0.30 sweep 實際變數是韻律權重。
- **追問：** 為什麼不能直接用該 F1 支持 CLIP？
- **追答：** 參數名稱和實驗程序不同，而且只有三部訓練影片，不可錯誤歸因。
- **誠實界線：** CLIP 原始分數未存入舊 cache，目前不能重做公平 CLIP sweep。

### MediaPipe

#### 15. MediaPipe 與 GRU 各負責什麼？
- **確認：** 是否能拆解偵測與時序分類。
- **直接回答：** MediaPipe 每幀偵測手部 landmark；GRU 讀取累積食指位置/位移序列並分類預設手勢類別。
- **追問：** GRU 輸入維度？
- **追答：** 20 個時間點、每點 4 維 `[x,y,dx,dy]`，輸出 5 類 logits 再轉 softmax/intent score。
- **誠實界線：** 手勢分類器未輸出講師語意意圖。

#### 16. 沒偵測到手時系統怎樣處理？
- **確認：** 是否知道缺測路徑。
- **直接回答：** 軌跡會清除或回 idle 類別，沒有手部視覺證據時手勢分數降低；OCR/CLIP 其他畫面訊號仍可存在。
- **追問：** 能不能推論這段不重要？
- **追答：** 不能；無手可能是遮擋、離開畫面或偵測錯誤。
- **誠實界線：** 目前沒有以「未偵測到手」當負面教學標籤訓練。

#### 17. ROI 和手勢分數如何影響畫面評分？
- **確認：** 是否理解從 tracking 到 scoring 的關係。
- **直接回答：** 達手勢觸發條件時，以手部中心裁 ROI，並將 combined visual score 乘 intent score；未觸發時用整幀視覺分析。
- **追問：** 0.7 代表 70% 教學意圖可信嗎？
- **追答：** 不是，這是程式門檻，不是經校準的概率。
- **誠實界線：** 門檻/映射目前是實驗設定，未以多教師資料驗證。

### SNR

#### 18. 你計算的是實測 SNR 嗎？
- **確認：** 是否理解估計假設。
- **直接回答：** 不是；用全片平均音框能量除以最低 10 百分位能量作 proxy。
- **追問：** 哪些狀況會偏差？
- **追答：** 全程有人說話、靜音比例不同、底噪非平穩或瞬間極低音量都可能破壞假設。
- **誠實界線：** 報告應稱「啟發式 SNR 估值」，不是物理真值。

#### 19. 10 dB 降噪門檻是否經驗證？
- **確認：** 是否能說明 pilot 限制。
- **直接回答：** 目前只是程式門檻；三部訓練影片估值都高於 20 dB，所以該條件在這三片未觸發。
- **追問：** 怎樣才可驗證？
- **追答：** 收集不同噪音型態的影片、人工音質標籤，固定評估流程比較觸發前後辨識錯誤與音質。
- **誠實界線：** 目前不能說 10 dB 是最佳門檻或已改善 Whisper。

### 韻律特徵

#### 20. 系統使用哪些韻律量？
- **確認：** 是否能指出每個特徵。
- **直接回答：** 字元/秒、RMS 平均音量、pyin F0 的相對標準差、低能量 frame 比例。
- **追問：** 哪個量最依賴 ASR？
- **追答：** speech rate 的分子是 Whisper 非空白字元數，所以辨識錯誤會影響它。
- **誠實界線：** pause ratio 是能量 proxy，不是完整語言停頓分析。

#### 21. 韻律為什麼不能直接等於重要性？
- **確認：** 是否知道描述性特徵與標籤的差別。
- **直接回答：** 大聲、慢速或音高變化只能描述說話方式，也受麥克風、個人習慣及情緒影響；不等於該知識點對學生更重要。
- **追問：** 為何仍納入？
- **追答：** 作為一種可檢驗輔助特徵，透過融合評估其增量價值，而非先驗認定它代表重要性。
- **誠實界線：** 現有樣本不足以確立這些特徵與學習效益因果關係。

### 特徵融合

#### 22. Adaptive Fusion 的公式是什麼？
- **確認：** 是否理解可靠度作用點。
- **直接回答：** \(\beta_{\mathrm{eff}}=\beta R_v\)，\(\alpha_{\mathrm{eff}}=1-\beta_{\mathrm{eff}}\)，\(S=\alpha_{\mathrm{eff}}s_t+\beta_{\mathrm{eff}}s_v\)。
- **追問：** 若可靠度為零？
- **追答：** 視覺權重為零，融合分數只剩文字分數。
- **誠實界線：** 可靠度本身是啟發式訊號組合，未經大樣本校準。

#### 23. 手算一次融合分數。
- **確認：** 是否能操作公式而非背誦。
- **直接回答：** \(s_t=.8,s_v=.6,\beta=.4,R=.5\)，所以 \(\beta_{\rm eff}=.2,\alpha_{\rm eff}=.8\)，\(S=.8×.8+.2×.6=.76\)。
- **追問：** 如果 \(R=1\) 呢？
- **追答：** 回到固定 0.6/0.4，加權結果 `.6*.8+.4*.6=.72`。
- **誠實界線：** 這是公式示例，不是某部影片的實際片段數據。

#### 24. α/β 的候選 0.5/0.5 是否正式採用？
- **確認：** 是否分清實驗與設定。
- **直接回答：** 不是；三部訓練影片搜尋候選 0.5/0.5、macro F1=0.5341，但程式仍以 0.6/0.4 作目前基準。
- **追問：** 為何不直接改成候選？
- **追答：** 樣本少、單人標註且容易選到資料特定參數，需另有代表性 validation/test 才能支持採用。
- **誠實界線：** 0.6/0.4 也不是已證明的最佳，只是目前實驗設定。

### MLP

#### 25. MLP 的 12 維輸入是什麼？
- **確認：** 是否核對 schema。
- **直接回答：** `s_text`、`s_visual`、visual reliability、gesture score、prosodic score、availability mask、六個 teaching-stage one-hot，共 12 維。
- **追問：** mask 有什麼作用？
- **追答：** 區分實際測得中性分數 0.5 和缺資料時填入的 0.5，避免模型把缺測當成真觀測。
- **誠實界線：** stage 未分類時六維 one-hot 為全零，並不是第七個 stage。

#### 26. MLP 的網路與訓練配置？
- **確認：** 是否了解模型結構和學習目標。
- **直接回答：** 12→32→16→1，兩層 ReLU、Dropout 0.3、sigmoid；BCELoss、Adam，正標籤依 segment/GT overlap ratio 至少 0.5。
- **追問：** sigmoid 輸出是校準機率嗎？
- **追答：** 不一定；它是模型分數，未做 calibration。
- **誠實界線：** 當前 checkpoint 是小樣本實驗，不足以宣稱通用。

#### 27. MLP 為什麼沒有設為預設？
- **確認：** 是否知道實驗結果和工程旗標。
- **直接回答：** `USE_MLP_FUSION=False`；四部影片、三片訓練/驗證及單人標註不足以證明 MLP 泛化。
- **追問：** test 結果如何？
- **追答：** 新 12 維 MLP 在 `test_10min` 評估一次 F1=0.500；此影片另有較早 β 掃描歷史，不能視為全程 untouched。
- **誠實界線：** 不把這個 F1 說成提升，也不再用該 test 選參。

### 模型訓練

#### 28. 為何依影片分組切 train/validation？
- **確認：** 是否理解資料洩漏。
- **直接回答：** 同影片相鄰片段高度相似；若隨機拆 segment，模型可能記住影片特性。以 video ID 分組可讓同一影片只屬 train 或 validation。
- **追問：** 程式怎麼實作？
- **追答：** `groups` 對應每個片段，先 shuffle unique group，分出一部分 group 作 validation，再以 mask 建立索引。
- **誠實界線：** 只有三部訓練影片，group validation 估計仍非常不穩。

#### 29. Ground Truth 怎樣轉成 MLP label？
- **確認：** 是否理解監督信號。
- **直接回答：** 計算片段與標註區間的時間 overlap，預設用 overlap/GT duration 作基準，比例至少 0.5 標 1，否則 0。
- **追問：** 為何不是依片段長度作分母？
- **追答：** 現行預設 label basis 是 ground_truth，表示至少涵蓋一半標註重要區間；可配置 segment basis，但本實驗明確記錄採用的 basis。
- **誠實界線：** 二元化會丟失部分重疊程度資訊，0.5 門檻是實驗設計。

#### 30. 為什麼裁切 `eval_range_sec`？
- **確認：** 是否防止未標註片段污染評估。
- **直接回答：** 有些特徵檔包含完整影片，但 GT 只覆蓋有限範圍；訓練與測試都先裁到標註範圍並歸零時間，避免把無標註尾段納入選段預算。
- **追問：** 多片訓練特徵如何合併？
- **追答：** 每片各自裁切，再將片段和 GT 移到不重疊的合併時間軸，group ID 仍保留原影片。
- **誠實界線：** 若標註範圍本身偏差，裁切不會修正標註品質。

### 資料集與標註

#### 31. 現在有多少影片及標註者？
- **確認：** 是否掌握研究樣本限制。
- **直接回答：** 四部影片有 12 維特徵；三部用於 train/validation，一部作 test；現有 GT 是單人標註 pilot。
- **追問：** 標註者一致性怎樣？
- **追答：** 單人資料無法計算標註者間 Cohen’s Kappa，目前一致性仍待多標註者研究。
- **誠實界線：** 樣本數不能支持廣泛課程或教師族群泛化。

#### 32. 為什麼要保留影片 ID？
- **確認：** 是否理解群組與可追溯性。
- **直接回答：** 可做 group split，追蹤每片結果，也能避免相鄰片段洩漏。
- **追問：** 若影片是同一老師不同課程呢？
- **追答：** 可能仍共享教師/場景偏差；更嚴格的未來切分可按教師或課程群組，而不是只按影片。
- **誠實界線：** 現有分組策略只能控制影片層級洩漏，不保證教師層級獨立。

### 評估指標

#### 33. Recall、Precision、F1 分別回答什麼？
- **確認：** 是否理解摘要與 GT 的命中率。
- **直接回答：** Recall 看重要標註區間被涵蓋比例；Precision 看選入摘要的區間中有多少屬標註重點；F1 是兩者調和平均。
- **追問：** F1 為何用調和平均？
- **追答：** 當其中一項偏低時，調和平均會受到較大懲罰，不會被另一個高值簡單補償。
- **誠實界線：** 指標結果受 overlap hit 門檻、標註品質及時間範圍定義影響。

#### 34. FAR 與 TSR 提供什麼補充？
- **確認：** 是否考慮摘要長度及誤報。
- **直接回答：** FAR 描述選入非 GT 時間的比例；TSR 描述相對原片節省多少觀看時間。
- **追問：** 為什麼不能只看 F1？
- **追答：** 兩支摘要即使 F1 類似，片長和非重點內容可能不同；多指標能呈現取捨。

## 4. 口試自我介紹與專案介紹稿

### 30 秒版本

各位老師好，我的專案是 KeyTake AI，一套教育影片多模態摘要原型。系統以 Whisper 取得帶時間戳逐字稿，結合 TF-IDF/SBERT 文字特徵、OCR/CLIP 視覺線索、手勢軌跡和韻律估計，再依視覺可靠度調整模態權重，挑選片段並輸出摘要影片。現階段資料只有四部影片及單人標註，MLP 仍停用，結果屬探索性驗證；研究重點是建立可分析的系統流程，而不是宣稱已證明效能提升。

### 1 分鐘版本

各位老師好，我研究的問題是教學影片太長，學生回顧時不容易定位重點。KeyTake AI 是一個以片段時間對齊為核心的多模態摘要系統。Web 端由 FastAPI 接收影片，預設交給 Celery/Redis 處理；FFmpeg 標準化影片並抽音訊，Whisper 輸出帶時間戳逐字稿。文字側使用 TF-IDF 與 SBERT 形成相對語意分數，並估算語速、音量、音高變化和停頓比例；視覺側取片段三個影格，結合 MediaPipe 手部軌跡、OCR/文字比對與 CLIP。融合時以視覺可靠度調整視覺權重，再由選段器套用門檻和總長度預算，最後以 FFmpeg 輸出摘要與時間 mapping。現有四部影片、單人標註，三部訓練影片搜尋的 α/β 候選與韻律權重候選都只是探索結果，MLP 預設未啟用；我不把它們解讀為已驗證的效能提升。

### 3 分鐘完整專案介紹

各位老師好，我的專案 KeyTake AI 想處理的是教學影片長、學生複習時需要反覆搜尋片段的問題。我把摘要任務拆成「先在每個時間片段建立多模態線索，再融合排序，最後在時間預算內選段」。

第一步是系統資料流。使用者在瀏覽器選影片後，前端以 multipart POST 到 FastAPI。後端檢查副檔名及檔案大小，以 UUID 暫存，預設派送 Celery/Redis 背景工作。工作呼叫 `run_pipeline()`，所以 CLI 和 Web 共用核心分析流程。完成後產生 `summary.mp4`、片段索引和 timeline mapping，前端輪詢狀態並呈現索引、時間軸、原片/摘要長度與節省比例。

第二步是多模態特徵。FFmpeg 將音訊轉成 16 kHz mono WAV，系統使用能量分位數估計 SNR，低於 10 dB 才做頻譜減法。這是 proxy，不是參考訊號量測的實際 SNR。Whisper 預設使用本機 base 模型，輸出 `{start,end,text}`。這些時間戳讓文字、視覺、韻律與剪輯在同一時間軸上對齊。文字評分的 SBERT 模式把 TF-IDF 與對教學提示語料的 cosine 合併；另以 librosa 估算字元率、RMS、F0 變化和低能量比例。視覺側對每個語音片段取 25%、50%、75% 三幀，使用 MediaPipe 追蹤食指、Kalman 平滑和 GRU/規則分類；ROI 文字由 Tesseract 偵測，OCR 文字與逐字稿關鍵字比較，也可使用 CLIP 做圖文 cosine 對齊。

第三步是融合和輸出。Adaptive Fusion 把視覺可靠度乘到基礎視覺權重，視覺資料不可靠時就降低視覺影響。比如文字分數 0.8、視覺 0.6、β=0.4、可靠度 0.5，視覺有效權重為 0.2，最後分數是 0.76。韻律分數只在可用時作中心化倍率微調。系統也實作 12 維 MLP，但目前 `USE_MLP_FUSION=False`。選段不只是排序：它會先過分數門檻、合併或切分區段，再受原片長 60% 的預設預算限制，最後依原片時間順序輸出。FFmpeg 剪輯後建立 source/output mapping，讓前端摘要時間軸能正確跳轉。

最後是研究限制。現有四部影片有 12 維特徵，三部用於訓練/驗證，一部 `test_10min` 的 MLP 新評估 F1 為 0.500；但該影片有較早 β 掃描紀錄，不能說是完全未觸碰測試集。α/β 的 0.50/0.50 和韻律權重 0.30 是三片訓練資料上的探索候選，不是正式最佳值；0.5611 的結果屬韻律權重 sweep，不是 CLIP sweep。加上單人標註限制，我只把目前成果定位為可工作的研究原型與初步量測，未宣稱效能提升已獲證明。下一步應擴增影片、加入雙標註者、固定未使用過的 test set，再檢驗各模態的增量價值。

### 5 分鐘技術架構介紹

各位老師好，以下我從資料契約、特徵工程、融合、選段和評估限制說明 KeyTake AI。

系統的最小資料單位是帶時間範圍的片段。Whisper 產生 start/end/text，其他模態都依這個片段時間計算，這樣才有共同的 join key。Web 前端 POST 影片後，FastAPI 以 UUID 儲存並交給 Celery/Redis；核心管線由 `main.run_pipeline()` 執行。API 狀態輪詢和摘要檔案輸出分離，因此影片分析不會阻塞整個 HTTP request。

音訊前處理由 FFmpeg 抽取 16 kHz mono WAV。SNR 函式把全片平均 frame power 除以低能量分位數，取 10 log10。此值只是假設低能量 frame 代表 noise floor 的估計，不能視作有 clean reference 的 SNR。小於 10 dB 時才啟動頻譜減法。Whisper 可選 local/remote；local 預設 base，remote 會傳音訊至外部 API。轉錄結果僅做有效時間檢查和相同文字高重疊合併，沒有通用 hallucination filter。

文字分數分成兩個互補特徵。TF-IDF 反映詞在本批文件中的相對權重；SBERT 對片段與提示語料編碼，取 cosine 最大相似度。預設混合係數各半，輸出供排序的 `s_text`，不是機率。韻律分析以 ASR 範圍裁音訊，計算字元/秒、RMS、pyin F0 相對標準差及低能量比例，依本片有效段落 P10/P90 正規化。缺失值以中性 0.5 填補但 availability mask 為 false。這些特徵描述表達行為，不能直接視為教學價值。

視覺路徑每段取 25%、50%、75% 影格。MediaPipe 偵測手部 landmark，程式取第一隻手食指尖並以 Kalman 平滑；GRU 收 20×4 序列分類五種預定義軌跡類別。達到觸發門檻時以手部中心裁 ROI，否則看整幀。Tesseract 取得文字框及 OCR，再與 ASR 關鍵字比對；CLIP 使用預訓練 image/text encoder 算 cosine。Cosine 是 embedding 對齊，不是教學重要機率。另有視覺可靠度估計手部穩定、文字密度、接近度和可用 confidence；但目前 tracker 未傳出 MediaPipe confidence，估計器會對剩下的有效訊號重整權重。

預設融合是解析式 Adaptive Fusion。假設文字分數 \(s_t\)、視覺分數 \(s_v\)、可靠度 \(R_v\)，基礎權重 α、β 且總和為 1，程式把視覺有效權重設為 \(\beta R_v\)，文字權重為其餘部分。若 \(s_t=.8,s_v=.6,\beta=.4,R_v=.5\)，分數為 \(.8×.8+.2×.6=.76\)。韻律特徵可在有效時再以 0.5 為中性點乘上微調倍率。MLP 是另一條互斥路徑，輸入五個連續分數、availability mask 與六階段 one-hot，共 12 維；模型結構為 12→32→16→1。但它尚未設為預設。

選段器先依分數底線及中位數門檻建立候選，合併相鄰片段、限制單段長度，再按分數優先填入 `duration×MAX_SUMMARY_RATIO` 的預算，最後按時間排序。因此高分不一定會入選。FFmpeg 加上前後 padding、合併重疊剪輯、重編碼並串接。輸出的 timeline 對應 source 與 output 區間，前端用該映射在摘要影片中跳轉；索引則保持原片時間。

評估方面，12 維特徵來自四部影片，三部訓練/驗證、一部 `test_10min`。訓練依影片 ID 分組，避免相鄰片段洩漏；標註範圍以 `eval_range_sec` 裁切，測試預算不延伸到未標註尾段。三片 α/β 搜尋的候選 0.50/0.50、macro F1 0.5341；韻律權重 sweep 候選 0.30、macro F1 0.5611。後者不是 CLIP sweep。新 MLP 在 `test_10min` 一次 F1=0.500，但歷史 README 有過 β 掃描，因此不能聲稱該集完全 untouched。資料量和單人標註使所有結果都屬探索性，不能宣稱已證明泛化或效能提升。未來我會擴充教師與課程、增加標註者、固定獨立測試集並預先規劃消融比較。
